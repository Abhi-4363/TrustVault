# TrustVault — Security Threat Model & Risk Catalog

> **Version**: 1.0.0 (Stage 1 Initial Threat Baseline)  
> **Classification**: Internal Architectural Security Assessment  
> **Status**: All items marked **Planned** or **Unverified** until proven by implementation and automated tests.

---

## 1. Security Philosophy & Principles

TrustVault handles sensitive corporate records. The platform's security architecture adheres to the following foundational principles:

1. **Principle of Least Privilege**: Users and services must possess only the minimum permissions necessary to perform their roles.
2. **Defence in Depth**: Redundant security controls at network, application, authorization, and data storage layers.
3. **Fail-Safe Defaults**: Access requests are denied by default unless explicit permission is validated.
4. **Zero Implicit Trust for Storage**: Document binaries must never reside in web-accessible static directories.
5. **Complete Auditability**: Every access, modification, authorization change, and revocation must produce an immutable audit log.
6. **No Security through Obscurity**: Guessable or unguessable object IDs (UUIDs) do not replace robust authorization checks.

## 2. Threat Classification Matrix

| Threat # | Threat & Vector | Assets Affected | Attack Scenario | Planned Mitigation | Planned Automated Test | Current Status | Accepted Limitations & Reasons |
| :---: | :--- | :--- | :--- | :--- | :--- | :---: | :--- |
| **THREAT-01** | **Unauthorised Document Access** | Document content, Confidential metadata | An authenticated or unauthenticated attacker accesses a document URL or API endpoint without having been granted read access. | Enforce server-side authorization middleware on all document endpoints. Verify user membership in document access control lists (ACL) prior to fetching bytes. | Integration test asserting `403 Forbidden` when non-permitted user requests `/api/documents/:id`. | **Planned (Stage 4)** | In Stage 1, no document endpoint exists yet. Demonstration data is strictly client-side. |
| **THREAT-02** | **Insecure Direct Object References (IDOR) & ID Guessing** | Private document records | Attacker observes an incremental ID (e.g., `/api/documents/104`) or guesses UUIDs to access documents belonging to other tenants. | 1. Use cryptographically secure random UUIDv4 or MongoDB ObjectIds.<br>2. Strictly decouple object identification from authorization: every query enforces `{ _id: docId, ...authorisationFilter }`. | Automated test generating sequential/random IDs; asserts `404 Not Found` or `403 Forbidden` without leaking document existence. | **Planned (Stage 4)** | UUIDs alone do not prevent IDOR; authorization checks at the database query level are required. |
| **THREAT-03** | **Permission Revocation Lag (Stale Authorisation)** | Confidential document streams | An administrator or owner revokes user access, but the user continues reading or downloading the file due to cached tokens or long-lived download links. | 1. Direct authorization check against database on every download stream request.<br>2. Expire short-lived presigned/signed access tickets in <= 60 seconds.<br>3. Invalidate active session cache upon revocation event. | Automated test that grants access, fetches document, calls revoke endpoint, and immediately asserts subsequent request fails with `403`. | **Planned (Stage 5)** | Real-time WebSocket or Server-Sent Events push revocation to frontend UI is deferred to later stages. |
| **THREAT-04** | **Publicly Accessible File URLs** | Raw document binary files (PDFs, DOCX, images) | Web server serves the `uploads/` directory as static public files via `express.static()`. Attacker scans URL path to download files directly. | 1. Binary storage directory is kept strictly outside public web roots.<br>2. Document downloads are served strictly through an authenticated Express streaming controller (`res.sendFile` or stream) with headers `Content-Disposition: attachment; filename=...` and `X-Content-Type-Options: nosniff`. | Test attempting direct HTTP GET to static paths (e.g., `/uploads/secret.pdf`); asserts `404 Not Found`. | **Planned (Stage 3)** | Stage 1 contains zero static file serving routes and no live upload ingestion. |
| **THREAT-05** | **Audit-Log Modification or Deletion** | Audit trail integrity, Compliance records | Malicious user or compromised admin attempts to delete or alter logs documenting their unauthorized activities. | 1. Audit logs stored in an append-only collection.<br>2. Disallow `UPDATE` and `DELETE` operations on audit collections in the database layer / ORM hooks.<br>3. Cryptographic hash chaining or write-only service role. | Test asserting that `DELETE` or `PUT` endpoints against `/api/audit` do not exist (return `405` or `404`), and schema pre-hooks reject updates. | **Planned (Stage 6)** | Tamper-evident blockchain/external WORM storage is out of scope for the hiring challenge; append-only schema constraints are applied. |
| **THREAT-06** | **Privilege Escalation** | Tenant administration, User roles | A standard employee manipulates request parameters (e.g., `role: "admin"` in a profile update payload) to gain administrative privileges. | 1. Strict schema validation (Joi or Zod) disallowing client-supplied role mutations.<br>2. Administrative routes protected by `requireRole('admin')` middleware verifying token payload against database state. | Test asserting standard user sending `{ role: 'admin' }` receives `400 Bad Request` or role field is ignored. | **Planned (Stage 2)** | Roles are not yet implemented in Stage 1. |
| **THREAT-07** | **Malicious or Oversized Uploads** | Server disk, Memory, Host file system, Client execution | Attacker uploads a 2GB file to cause Denial of Service (DoS), or uploads an executable (`.exe`, `.sh`) masquerading as a `.pdf`. | 1. Enforce strict upload limits (e.g., 25MB max file size).<br>2. Validate MIME type using magic number inspection (file header signature) rather than user-supplied file extension.<br>3. Store files under randomized internal hashes rather than original filenames. | Test uploading 50MB file expecting `413 Payload Too Large`; test uploading disguised `.exe` expecting `415 Unsupported Media Type`. | **Planned (Stage 7)** | Antivirus scanning daemon (ClamAV) is an accepted limitation in local development environments. |
| **THREAT-08** | **Cross-Site Scripting (XSS)** | User session cookies, DOM integrity | Malicious document title, description, or comment containing `<script>` executes in another user's browser session. | 1. React JSX auto-escaping for all rendered variables.<br>2. Backend string sanitisation and schema stripping.<br>3. Content Security Policy (CSP) headers applied via Helmet middleware. | Test submitting payload `<script>alert(1)</script>` into document title; verify rendered text is escaped and no script evaluates. | **Planned (Stage 1 & 7)** | Frontend currently uses React which escapes variables by default. Helmet will be added to backend in Stage 2. |
| **THREAT-09** | **Cross-Site Request Forgery (CSRF)** | Document sharing actions, Access grants | Attacker lures an authenticated user to a malicious site that secretly submits a form granting the attacker edit access. | 1. Use stateless JWTs in `Authorization: Bearer` headers (immune to standard browser form CSRF) OR `SameSite=Strict` cookies with CSRF token verification.<br>2. Enforce strict CORS policies restricted to trusted `CLIENT_URL`. | Test sending cross-origin POST request with missing or spoofed Origin header; asserts rejection. | **Planned (Stage 2)** | Bearer token pattern preferred to simplify CSRF immunity while keeping mobile compatibility. |
| **THREAT-10** | **Session or Token Theft** | User account identity | Attacker intercepts unencrypted traffic or reads unencrypted tokens from browser storage via XSS. | 1. Enforce TLS/HTTPS in production.<br>2. Short JWT expiration (e.g., 15 minutes) with refresh token rotation.<br>3. Store tokens in secure `HttpOnly`, `SameSite=Lax/Strict` cookies or transient memory. | Automated test verifying expired tokens are rejected with `401 Unauthorized`. | **Planned (Stage 2)** | In Stage 1 development environment, HTTP is used locally on localhost. |
| **THREAT-11** | **Search Results Leaking Document Metadata** | Confidential document titles, Tags | Document search query indexes documents across all users; unauthorized user searches keyword and sees titles of confidential documents they cannot access. | Search query filters must always include the current user's authorization access criteria in the database query pipeline before returning metadata. | Automated test where User B searches for keyword in User A's private doc; asserts 0 results returned. | **Planned (Stage 7)** | Full-text search engine (e.g., Atlas Search / Elastic) will be bounded by tenant and user ACL filters. |
| **THREAT-12** | **Concurrent Permission Changes & Stale Decisions** | Document authorization states | Admin A revokes access while Admin B is updating permissions, or user initiates download during permission write. | 1. Use atomic database operations (`$set`, `$pull`) for ACL mutations.<br>2. Optimistic concurrency control via version keys (`__v`).<br>3. Verify authorization immediately prior to streaming bytes. | Concurrency integration test executing parallel revoke and read requests; asserts no leaked bytes. | **Planned (Stage 5)** | Extreme distributed lock scenarios are simplified using MongoDB atomic document-level operations. |

## 3. Threat Model Maintenance & Verification Protocol

1. **Before Any Feature Development**: Review relevant threats above and implement required mitigations as part of the feature, not as an afterthought.
2. **After Feature Completion**: Execute automated security test suite and update status from `Planned` to `Verified`.
3. **Audit Trail**: Every change to this threat model must be recorded in Git with rationale and reviewer approval.
